# 0007 — API key authorizer, not Cognito

## Context

The HTTP API had no authentication: anyone who found the URL could write to the
registry. That had to change before the service could be exposed anywhere.

Two options were considered seriously.

**Cognito User Pool with the HTTP API's native JWT authorizer.** The AWS default
answer. API Gateway validates the JWT itself, so no authorizer code exists to
maintain. It brings user records, password policy, MFA and token refresh for free.

**A Lambda authorizer validating a shared API key.** A small function checking a
header against a secret.

## Decision

The Lambda authorizer with a shared API key, held in AWS Secrets Manager and
generated by CloudFormation at deploy time.

## Consequence

The deciding argument is what is actually calling this API. A device registry is
machine-to-machine. Devices do not do interactive sign-up, do not have email
addresses, do not answer MFA challenges and do not refresh OAuth tokens on a
schedule. API keys — or mutual TLS at higher assurance — are the correct pattern
for a device plane. Cognito is the right answer for a human-facing admin console,
and this repository does not have one. Choosing Cognito here would have been
choosing the AWS default over the appropriate design.

Two secondary consequences follow, both real. It stays inside the free tier:
Secrets Manager is about $0.40 a month, and there is no user directory to run. And
it is demonstrable — a reviewer pastes one header into `curl` and gets a 200,
where a JWT flow requires standing up a user and completing a login before seeing
anything work. For a portfolio project that has to survive a ninety-second skim,
that difference matters.

What this gives up is per-caller identity. The key is shared, so a request cannot
be attributed to a specific device, and revoking one caller revokes all of them.
There is no expiry, so a leaked key is valid until someone rotates it. That is
acceptable for a single-consumer `dev` environment and is recorded in the README's
security table rather than glossed over — it is the top item in Future
Improvements.

**When to revisit.** Two triggers, either of which flips the decision:

1. **A web console or any human user.** The moment a person logs in, Cognito's
   user directory, password policy and MFA stop being overhead and start being the
   product. Rolling that by hand would be a mistake.
2. **Per-device ownership or scoping.** If devices belong to tenants and a caller
   may only see their own, identity has to be per-caller and carried in the
   request. That is a JWT with claims, not a shared secret — and it also forces
   the pagination token to be signed (see
   [0006](0006-opaque-pagination-token.md)).

Until one of those arrives, adding Cognito would double the auth surface and the
template size for a capability nothing in this system uses.

## Implementation notes worth keeping

Three details that were deliberate, not incidental:

- **Constant-time comparison** (`hmac.compare_digest`). A plain `==` returns on the
  first differing byte, which leaks the length of a correct prefix to anyone who
  can time responses.
- **Fails closed.** A missing secret, an AWS error or a malformed event returns
  `isAuthorized: False` rather than raising. An unhandled exception in an
  authorizer becomes a 500, which some clients retry — and failing open would
  defeat the authorizer entirely.
- **The AWS SDK loggers are pinned to INFO.** botocore logs response bodies at
  DEBUG, and the `GetSecretValue` body contains the key in clear text. `LOG_LEVEL`
  is operator-controlled, so raising it to chase an unrelated bug would otherwise
  have written the API key into CloudWatch. A test fails if that mitigation is
  removed.
